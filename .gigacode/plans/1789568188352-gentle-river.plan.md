# План доработки кластерного теста OrderedSetOperationsTest

## Целевой файл
`src/test/java/com/hurricache/client/cluster/smart/OrderedSetOperationsTest.java`

## Базовые правила (согласно требованиям)

1. **KeyHintData**: Всегда использовать `KeyHintData`, возвращаемую методом `create`
2. **Задержка после создания**: 100ms для обычных объектов, ~1000ms для больших (≥1000 элементов)
3. **Паттерн проверки репликации**:
   - Write на MASTER → проверить на MASTER → задержка → проверить на BACKUP
   - Write на BACKUP → проверить на BACKUP → задержка → проверить на MASTER
4. **Проверка setTtl**: Write на мастере → проверить на мастере → задержка → проверить на бэкапе (и наоборот)
5. **Проверка блокировок**: Аналогично setTtl
6. **Задержка перед проверкой на соседе**: Только если write была на одном узле, а проверка на другом
7. **TTL expiration**: Проверить истечение на мастере и на бэкапе
8. **Lock expiration**: Проверить истечение на мастере и на бэкапе

## Найденные проблемы

### P1: Large object creation — недостаточная задержка репликации
**Метод**: `testCreateLargeOrderedSetWithChunking`
**Проблема**: После создания 1500-элементного набора используется `Thread.sleep(100)` — недостаточно для репликации большого объекта.
**Исправление**: Заменить на `Thread.sleep(1000)`.

### P2: `testAddElementWithWeightEmptyList` — отсутствует проверка репликации на соседний узел
**Проблема**: Нет задержки после создания, нет проверки на MASTER после write на BACKUP.
**Исправление**: Добавить `Thread.sleep(REPLICATION_DELAY_MS)` после создания. Добавить проверку на MASTER.

### P3: `testStreamElementInRangeOrderedSet` — первая операция это read, не write
**Проблема**: Тест выполняет `streamElementInRangeOrderedSet` (read) как "write on BACKUP". Это не write операция.
**Исправление**: Добавить write-операцию (`addElementWithWeight`) на BACKUP, затем проверить репликацию на MASTER.

### P4: `testStreamElementInRangeOrderedSetReverse` — нет проверки репликации
**Проблема**: После read на BACKUP нет проверки репликации на MASTER.
**Исправление**: Добавить `addElementWithWeight` на BACKUP → задержка → проверка на MASTER.

### P5: `testStreamElementInRangeOrderedSetNoMatch` — нет проверки репликации
**Проблема**: После read на BACKUP нет проверки репликации на MASTER.
**Исправление**: Добавить `addElementWithWeight` на BACKUP → задержка → проверка на MASTER.

### P6: `testSetTtlAndGetTtl` — нет явной проверки setTtl на MASTER
**Проблема**: setTtl сначала ставится на BACKUP, потом на MASTER. Но нет отдельной проверки: setTtl на MASTER → verify на MASTER → verify на BACKUP.
**Исправление**: Добавить явный блок "setTtl on MASTER" с полной проверкой репликации.

### P7: `testTtlExpirationOnMaster` — TTL ставится при создании, а не отдельно
**Проблема**: TTL (2000ms) ставится сразу после create, что затрудняет разделение тестовых шагов.
**Исправление**: Разделить: create → задержка → setTtl на MASTER → задержка → verify на MASTER → задержка → verify на BACKUP.

### P8: `testTtlExpirationOnBackup` — аналогично P7, TTL ставится на BACKUP
**Исправление**: create → задержка → setTtl на BACKUP → задержка → verify на BACKUP → задержка → verify на MASTER.

### P9: Lock tests — дублирование кода для CANT_UNLOCK
**Проблема**: Код для проверки CANT_UNLOCK повторяется в каждом lock-тесте.
**Исправление**: Вынести в приватный хелпер-метод.

### P10: `testLockExpirationOnMaster` — нет явной проверки lock на MASTER после создания
**Проблема**: Lock ставится на MASTER, но проверка "client 1 can write" — это read-проверка (streamOrderedSet). Нужно явно проверить write-доступ.
**Исправление**: Добавить `addElementWithWeight` с OWNER_CLIENT_ID на MASTER, verify на MASTER, задержка, verify на BACKUP.

### P11: `testLockExpirationOnBackup` — create на BACKUP использует `bytes(key)` вместо `key`
**Проблема**: `client.setMode(Mode.BACKUP).createOrderedSet(bytes(key), ...)` — inconsistent с остальными тестами.
**Исправление**: Использовать `key` (String) для createOrderedSet, как в остальных тестах.
